# Tasks

## 1. Read queries

- [x] 1.1 Add a read-only rocket repository in `internal/repository` with a single-rocket query and a list query. Both select only launched or exploded rows (`rocket_type IS NOT NULL OR explosion_reason IS NOT NULL`) and do not filter channels. The list takes its `ORDER BY` from a fixed allow-list (`channel`, `type`, `mission`, `speed`, `status`, `launchedAt` × `asc`/`desc`, text `COLLATE "C"`, `NULLS LAST` in both directions, `channel ASC` as tie-breaker). Verify with integration tests: a row with only speed changes is not returned, a launched exploded rocket is returned, an exploded rocket without launch is returned with `NULL` launch fields and fills them in after its launch is processed, every sort field works in both directions with `NULL` rows last, ties are ordered by channel, and an empty table gives an empty list.
- [x] 1.2 Expose the channel rule from `internal/domain` as one function used both by `Classify` and by the read path, without changing processing behavior. Verify with the existing classification table tests and a direct table test of the function under `go test -race ./internal/domain`.

## 2. HTTP endpoints

- [x] 2.1 Add `GET /rockets/{channel}` in `internal/handler`. It defines its read interface and maps rows to the JSON representation (camelCase fields, `status` from the explosion reason, RFC 3339 UTC times, every field present with `null` launch fields for an exploded rocket without launch). Times are formatted with `time.Format(time.RFC3339Nano)` in UTC, never `MarshalJSON`. It answers `404 {"error": "rocket not found"}` for missing rockets, for a differently cased channel, and for channels breaking the domain rule (without calling the repository). It answers `503` when the database is unavailable or the 5 s read deadline expires, and `500` otherwise. A cancelled client request is logged at debug level only. Verify with unit tests against a fake repository under `go test -race ./internal/handler`, covering `a%2Fb`, `%E2%82%AC`, a launch time in year 10000 and in year -1 UTC, a nanosecond time, a timeout and a cancelled context.
- [x] 2.2 Add `GET /rockets` in `internal/handler`. It returns `{"rockets": [...]}` (an empty array, never `null`) and drops rows whose channel breaks the domain rule while keeping the order of the rest. It parses the query with `url.ParseQuery`, applying the `sort` and `order` defaults. It answers `400` naming the parameter for unknown, wrongly cased, empty or repeated values, and `400` naming the cause for a query string `url.ParseQuery` rejects (`sort=%zz`, `sort=speed;order=desc`). Other parameters are ignored. Verify with unit tests for each accepted value, each `400` case, the `503`/`500` paths, and a fake result mixing valid and invalid channels (`a.b`, `€`, `a\n`) whose order survives filtering.
- [x] 2.3 Register both routes in `internal/server.Routes` and wire the repository in `cmd/rockets/server.go`. `HEAD` must be served like `GET`, and other methods on `/rockets` and `/rockets/{channel}` must get `405` with `Allow: GET, HEAD`. Verify with server tests: `GET`/`HEAD` reach the handlers, `POST /rockets` and `DELETE /rockets/c1` → `405`, `GET /rockets/` and `GET /rockets/c1/x` → `404`, `GET /rockets/./c1` → `307` to `/rockets/c1`. Add an integration test that reads processed state through the real server and database, including a launched historical row with channel `a.b` inserted directly: it is absent from the list, `404` by channel, and still in the table.
- [x] 2.4 Document both endpoints in `README.md`: the representation, sorting parameters, errors, read lag behind intake, which rockets are visible (launched or exploded; hidden without either and with invalid channels), `null` launch fields and the later speed jump of an exploded rocket without launch, `lastMessageNumber` meaning, sender-clock times with microsecond precision, the unbounded list, `speed` beyond 2^53 for JavaScript clients, nginx retrying `503` reads, and the absence of CORS and caching headers. Replace the "future read API must hide" note with the implemented behavior. Verify that the documented `curl` commands run against the compose stack.
